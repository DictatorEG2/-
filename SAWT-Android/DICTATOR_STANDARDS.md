# ثوابت Dictator — معيار إلزامي لمشروع صَوْت

هذا الملف جزء من مواصفات المشروع، وتُطبَّق قواعده على كل تعديل لاحق. لا تُعتبر الميزة مكتملة لمجرد إضافة واجهتها؛ يجب تنفيذها واختبارها وتوثيق حدودها.

## 1. الأداء وقاعدة البيانات
1. إنشاء فهارس لأعمدة البحث والترتيب المتكرر، مع مراجعة أثر الفهرس على الكتابة وحجم قاعدة البيانات.
2. منع نمط N+1؛ استخدم JOIN أو استعلامات مجمعة/دفعات مناسبة عند وجود علاقات.
3. منع `SELECT *`؛ اطلب الأعمدة المطلوبة فقط.
4. قوائم البيانات القابلة للامتداد: 20 عنصرًا في الصفحة مع إجراء «تحميل المزيد»، ما لم تكن القائمة صغيرة وثابتة بطبيعتها.
5. تخزين البيانات الثابتة نسبيًا مؤقتًا، مع سياسة إبطال واضحة عند التعديل أو انتهاء الصلاحية.
6. تجنب العمل الثقيل على Main Thread، وراقب استهلاك الذاكرة والبطارية والشبكة.

## 2. التحديثات وإصدارات Android
1. استخدام GitHub Releases العام لفحص التحديثات وتنزيل APK؛ لا خادم خاص مطلوب.
2. عدم تضمين GitHub Tokens أو أي أسرار أو مفاتيح توقيع داخل المصدر أو APK.
3. توقيع كل إصدار من التطبيق بالمفتاح نفسه؛ فقدان المفتاح أو تغييره يمنع التحديث فوق النسخة المثبتة.
4. حفظ keystore وكلمات مروره خارج المستودع وملفات APK، مع نسخة احتياطية آمنة لدى المطوّر.
5. رفع `versionCode` في كل إصدار، ومزامنة `versionName` مع وسم Release الرقمي.
6. عدم التثبيت الصامت؛ يعرض Android مثبت الحزم ويظل قرار التثبيت للمستخدم.
7. قبول روابط تنزيل HTTPS موثوقة فقط، والتحقق من وجود APK صالح قبل عرض التحديث.
8. توثيق اسم المستودع الفعلي قبل النشر؛ لا تُترك قيمة افتراضية أو تخمينية في إصدار عام.

## 3. الخصوصية والأمان
1. أقل مجموعة أذونات ممكنة، مع شرح واضح لكل إذن قبل طلبه.
2. لا تسجيل صوتي مستمر ولا تخزين/رفع للصوت أو نصوص الأوامر أو محتوى الشاشة دون حاجة معلنة وموافقة صريحة.
3. العمليات الحساسة تتطلب تأكيدًا واضحًا، ولا تنفّذ مكالمات أو رسائل أو إجراءات خارجية دون إذن المستخدم.
4. عدم تسجيل كلمات المرور أو الأرقام أو النصوص الخاصة في السجلات. سجل الأخطاء تقني ومحدود الحجم.
5. تحديث `PRIVACY.md` كلما تغير سلوك الشبكة أو التخزين أو الأذونات أو المعالجة الصوتية.

## 4. جودة الكود والتسليم
1. مراجعة الأخطاء والحالات الحدية قبل وبعد كل تعديل.
2. إزالة التكرار والكود الميت والاستيرادات غير المستخدمة دون حذف سلوك قائم.
3. الحفاظ على بنية المشروع وأسلوبه؛ لا إعادة كتابة واسعة بلا ضرورة.
4. عدم كسر ميزة سليمة عند إضافة ميزة جديدة؛ أضف اختبارات انحدار مناسبة.
5. تشغيل اختبارات الوحدات والبناء عند توفر البيئة، وتوثيق ما لم يُنفَّذ بوضوح.
6. لا يُعلن عن إصدار مستقر قبل نجاح البناء والاختبارات الأساسية والتحقق على جهاز فعلي للوظائف الحساسة.
7. استخدام CI لبناء المشروع وتشغيل الاختبارات عند كل Pull Request وتغيير على الفروع الأساسية.

## 5. واجهة وتجربة الاستخدام
1. واجهة احترافية متناسقة وليست HTML أو طفولية؛ RTL صحيح في كل الشاشات.
2. الالتزام بنظام الألوان والخطوط والمسافات والمكونات الموجود في `DESIGN_SYSTEM.md`.
3. حالات التحميل والنجاح والخطأ وعدم الإتاحة واضحة نصيًا، ولا تعتمد على اللون وحده.
4. الحفاظ على سهولة الوصول، ومساحات لمس مناسبة، وأوصاف دلالية للأيقونات.

## 6. قاعدة التغيير
قبل تنفيذ أي مهمة: راجع هذا الملف و`speed-rules.md` و`PRIVACY.md` و`TESTING.md`. بعد التنفيذ حدّث الوثائق والاختبارات المتأثرة، واكتب في سجل التغييرات ما تم وما لم يتم التحقق منه.
